Resources, what every term in this page means

Everything below is written for someone who knows very little about this specific research area. Nothing here assumes you've read a paper on knowledge editing before. If a word here uses another word from this glossary, that word is explained somewhere else in it too, not assumed.

The problem this whole project is about

Knowledge editing means changing one specific fact a language model believes, without retraining the whole model. Say a model was trained before a company changed its CEO, and it confidently says the old name. You don't want to retrain the entire model on billions of new words just to fix one sentence, that costs enormous time and money and risks quietly breaking things elsewhere. Knowledge editing is the field of methods that try to patch just that one fact, fast, cheaply, and without damaging anything else the model knows.

There are two broad families of approach. One changes the model's actual weights, the numbers inside the network that encode everything it knows, to bake the new fact in. The other leaves the weights untouched and instead gives the model an external note to check, closer to sticking a Post-it on the model rather than rewriting its memory. INLAY is the second kind. ROME, MEMIT, and AlphaEdit are the first kind.

How a language model works, just enough to follow the rest

A model like GPT-J or Qwen reads text as a sequence of tokens, roughly word-sized pieces, and for each position predicts a probability for every possible next token. Those raw, pre-probability numbers are called logits, one number per token in the model's vocabulary, and the token with the highest logit is usually what gets picked. The model's own unembedding is the internal table that turns its final internal representation into those logits, in effect the model's own dictionary of "if I want to say this word, push the logits in this direction." INLAY reuses that exact table to figure out which direction in logit space represents a given answer, then nudges the logits toward it when its memory fires. It never touches the model's actual learned weights, only the outputs it's about to produce.

An embedding is a way of turning a piece of text into a list of numbers, a vector, such that texts with similar meaning end up as similar vectors. A sentence embedding does this for a whole sentence at once rather than one word at a time. MiniLM is the specific, small, pretrained sentence-embedding model INLAY uses to turn a prompt into a vector, entirely separate from GPT-J or Qwen, it never gets trained or changed either.

Gradient is the quantity that tells a neural network which direction to nudge its weights during training, "make this number a little bigger, that one a little smaller, to get closer to the right answer." A gradient step is one such nudge. Training a model, or fine-tuning it on new data, means taking many thousands of these steps. INLAY is gradient-free, or takes zero gradient steps, meaning installing a fact never involves this process at all, which is exactly why it's fast, milliseconds instead of the seconds or minutes each gradient-based edit takes.

A frozen model is one whose weights are locked, nothing is allowed to update them. INLAY keeps the base model completely frozen and does all its work in a separate structure sitting beside it.

How INLAY's memory works

Product-key memory is the specific data structure INLAY stores facts in. Instead of one giant list of memory slots that would be slow to search, it splits addressing into two smaller lists, half-keys, and combines them, which makes searching millions of slots computationally cheap even though the actual number of facts stored might be tiny. Think of it like a library that doesn't shelve every book on one wall from A to Z, but files each book under a two-part code, a shelf number and a slot number, so you only ever have to scan two short lists to find any book instead of one enormous one.

A semantic key is the address INLAY uses to file a fact, computed from the sentence embedding described above rather than anything internal to the language model. Addressing this way is what lets the system recognize a paraphrase of a question as the same question, since paraphrases produce similar sentence embeddings even though the exact words differ.

A JL projection, short for Johnson-Lindenstrauss, is a fixed, never-trained mathematical operation that reshapes a vector from one size to another while mostly preserving how similar or different vectors are to each other. INLAY needs one because MiniLM's embeddings and the language model's internal dimension are different sizes, and this projection bridges them without any learning involved.

The gate is the decision INLAY makes at every single question: does a stored fact actually apply here, or should the base model just answer on its own? Three checks feed into this. The score is how closely the question's semantic key matches a stored fact's key, a plain similarity threshold. The margin checks that the best match beats the second-best match by a healthy amount, not just barely, which matters once several facts live in the same memory at once. The relation gate checks that the question is actually asking about the same relationship as the stored fact, not just mentioning the same subject, this is what stops the system from confidently answering a question about someone's birthplace using a fact that was actually about their job.

The benchmarks, what each one is actually testing

CounterFact is the most widely used knowledge-editing benchmark. Each example gives a model a fact it currently believes and a counterfactual replacement, for instance changing a country's capital to a different city, then checks whether the edited model adopts the new fact, whether it still recognizes the fact when the question is reworded, and whether editing this one fact accidentally changed the model's answer to unrelated nearby questions.

zsRE, zero-shot relation extraction, is a second, differently structured benchmark built from Wikipedia-derived question-answer pairs about entities and their relationships. It's used alongside CounterFact because a method that only works on one specific benchmark's style of question is a weaker result than one that works on two independently built ones.

RippleEdits tests something neither of the above does: whether an edit's logical consequences get correctly carried forward. If you edit a country's president, RippleEdits asks follow-up questions that only make sense if the model actually understood the new fact well enough to reason from it, not just recite it back verbatim. This is the one benchmark where INLAY's approach structurally struggles, because playing back a memorized answer isn't the same operation as deriving a new answer from a stored fact.

Sequential editing, sometimes called lifelong editing, tests what happens as you install many facts one after another into the same model without resetting anything in between, checking whether earlier edits survive and stay correct once dozens or hundreds more have been added on top.

Matched manifest means every method being compared was tested on the literal identical set of questions, drawn from real Wikidata entries and checked to make sure the underlying facts are actually real and verifiable, so no method gets an easier or harder sample than another by chance.

The metrics, what the numbers actually mean

Almost every score in this report is built from three underlying measurements. ES, efficacy, is simply whether the edit worked at all, ask the exact edited question, did the model give the new answer. PS, paraphrase, is the same check but with the question reworded, testing whether the model actually generalized the edit rather than just pattern-matching the exact sentence it was shown. NS, neighborhood or locality, is the opposite kind of check, ask a different but related question that should be unaffected by the edit, and see whether the model's answer stayed the same. A method that scores well on ES and PS but poorly on NS installed the fact but broke something nearby; the reverse means it protected everything else but the edit itself barely worked.

These three get combined into one score using a harmonic mean rather than a simple average. A harmonic mean punishes any single weak number much more than an average would, a method scoring perfectly on two of the three and zero on the third gets a harmonic mean near zero, not a flattering two-thirds. This is deliberate: a knowledge editor that aces two of the three checks and completely fails the third isn't a good editor, and the harmonic mean refuses to hide that.

N is simply how many examples a result is based on. A score from N=100 is a smaller, less certain sample than one from N=5000, which is why this report tracks N next to every number and why INLAY's score being nearly identical from N=100 all the way to N=5000 is itself evidence the result is real rather than a lucky small sample.

A held-out tune and test split is how the operating threshold, the gate's cutoff score, gets chosen honestly. The examples are split in two, one half is used to find the best-performing threshold, and only the other half, which that threshold has never seen, is used to report the final score. Picking a threshold using the same data you report your result on would inflate the number in a way that wouldn't hold up on new questions.

Token-accuracy and probability of success are two different, non-interchangeable ways of scoring whether an answer is correct, one checks whether the exact predicted tokens match, the other checks whether the correct answer simply had a higher probability than a wrong one without requiring it to be the literal top prediction. The second is a looser, easier bar to clear. Where this report flags a number with a dagger symbol, it's warning you that number was produced by the easier metric and shouldn't be read side by side with the harder one.

Write cost is how long installing one single fact takes, measured in milliseconds or seconds depending on the method. This is separate from how long the model takes to answer a question afterward, it's purely the cost of the edit itself.

The other methods, what each one actually does

ROME, Rank-One Model Editing, locates the specific layer inside the model responsible for a fact and applies a single, precisely calculated update to that layer's weights, a real gradient-based change to the model itself, not an external note.

MEMIT is ROME's successor, built to install many facts at once by spreading similar rank-one updates across several layers instead of just one, trading some single-edit precision for the ability to batch edits together.

AlphaEdit is a newer weight-editing method that specifically tries to protect everything the model already knows by mathematically projecting its updates away from the space of preserved knowledge, at some cost to how strongly any single edit gets installed.

WISE keeps the base model frozen but maintains a separate, trainable side-memory that gets merged into the model's computation at inference time, a middle ground between fully external memory and a full weight edit.

GRACE is the closest published relative to INLAY's own design, a table of discrete key-value slots attached to one layer, the key difference being GRACE addresses its slots using the model's own raw internal activations rather than an external sentence embedding, which this project's own testing found entangles unrelated topics together and is part of why GRACE scores near zero across this report's benchmarks.

RAG, retrieval-augmented generation, here used as an in-context editing baseline, simply hands the model the new fact as extra text in the prompt every time and lets the model reason over it directly, no memory structure, no weight change, the fact is just re-explained fresh on every single question.

Base means the completely unedited model, included as a floor, the score you'd get by doing nothing at all, so every other number in this report can be read against what "no editing happened" looks like.

Fine-tuning, mentioned as an early comparison, means training the model further with ordinary gradient descent on the new fact. It's included specifically to show catastrophic forgetting, the well-known failure where further training on a narrow new example damages the model's performance on everything unrelated to it, exactly the risk knowledge editing as a field exists to avoid.

The models this was all tested on

Every model here is described by its parameter count, written as a number followed by B for billion, the total count of individually adjustable numbers inside the network. More parameters generally means more capacity to store knowledge and handle nuance, at the cost of needing more computer memory and time to run. GPT-2 and GPT-2-XL (1.5 billion parameters) are older, smaller models used for the earliest, cheapest development and debugging of the method. GPT-J-6B (6 billion parameters) and Qwen2.5-7B and Mistral-7B (both around 7 billion parameters) are the three larger, modern models the final headline comparisons in this report are run on, chosen specifically because they come from three different organizations and architectures, so a result holding across all three is stronger evidence than a result on just one.

Research process terms that show up in the fine print

An ablation is an experiment where you remove or change exactly one piece of a method to measure what that piece was actually contributing, for instance turning the relation gate on and off to see precisely what it costs and what it buys. EasyEdit is the shared open-source software framework nearly every method in this report, INLAY's baselines included, gets run through, using one shared framework for scoring is part of what makes the comparisons in this report fair rather than each method being graded on its own generous curve.

A few outside papers get referenced directly in the build story above. Lample et al., 2019 is the paper that first proposed product-key memory as a technique, originally for adding capacity to a model during its own training, not for editing one afterward. Meta's Memory Layers at Scale, 2024 showed the same underlying structure scaling to enormous size in a production-grade pretraining setup. Larimar, from IBM and Princeton, ICML 2024, demonstrated that installing new knowledge into a model without any gradient steps at all was possible in the first place. kNN-LM is an older technique for having a model consult a stored dataset of examples at the moment it's generating text, an ancestor of the general idea of reading from an external memory. SERAC is a different, comparably-scoped knowledge editor mentioned for contrast, it handles a similar problem by training a completely separate small model to decide when to override the main one.

How INLAY was built

The method, the false starts that shaped it, where it borrows from the literature, and the real engineering that had to happen to get honest numbers out of it.

What it actually does

The base model never changes. Every edit is a write into an external table sitting beside a frozen transformer, addressed by a semantic key and retrieved by a normal forward pass. Writing a fact takes about 13 milliseconds and touches zero weights. Reading one is a single extra lookup added to whatever the model was already going to do.

Three design choices carry the whole method. The key is a frozen sentence embedding, not a hidden state pulled from inside the model, which is what lets it generalize across paraphrases without any training. The value is the answer's own unembedding direction, the same vector the model would use to predict that token anyway, so injecting it is just biasing logits, not surgery on activations. And the table itself is a product key memory: two small banks of half keys instead of one huge bank of full keys, which is what makes millions of addressable slots computationally cheap to search.

The evolution, in the order it actually happened

The first version keyed on the model's own hidden state at the last token of the written prompt. It looked reasonable and it was wrong in a specific, measurable way: a geometry probe found the paraphrase-versus-neighbor separation of that key was negative 0.035, worse than random. The raw hidden state rated a same-relation neighbor with a different subject as more similar to a genuine paraphrase than to itself. No threshold could ever separate a real hit from a false one with a key shaped like that, and it explained both the low paraphrase score and the leaky locality in one stroke.

The fix was to stop keying on anything internal to the model at all. Switching to a frozen MiniLM sentence embedding of the prompt, projected into the model's dimension with a fixed seeded random matrix, moved the same separation to positive 0.288, and CounterFact paraphrase generalization jumped from roughly 0.33 to 0.90 in the same stroke. Nothing about the model changed, only what the address was computed from.

The second real fix was about the value, not the key. Early versions injected a single unembedding direction added to every position, which capped efficacy at whatever the first token of the answer was and left multi-token answers unfinished. Switching to logit space playback, biasing each position toward the correct token of the stored answer sequence one at a time, is specifically what let the method beat ROME on zsRE (0.973 versus 0.908) rather than merely tie it.

Two gates were added after that, for different reasons. A margin gate compares the winning slot's score against the runner up's, which matters once more than one fact shares a memory table and is a genuine no-op in the single-edit protocol most of this project's numbers come from, since there is only ever one slot to compare against there. A relation gate compares the query's relation to the fired slot's relation by projecting out the shared subject direction from both. Turning it on cuts same-subject over-firing from 0.97 to 0.67, at a cost of paraphrase generalization dropping from 0.87 to 0.66. It ships off by default and is reported as an explicit, honestly bounded tradeoff rather than folded into the headline number.

Everything since has been scaling the same mechanism to bigger, more varied models: GPT-2, GPT-2-XL, GPT-J-6B, Qwen2.5-7B, and Mistral-7B, with only the alpha injection strength recalibrated per model and no other retuning required.

Where this sits in the literature

None of the three pieces are new in isolation. Product key memory is Lample et al., 2019, and Meta's Memory Layers at Scale, 2024, scaled the same structure to 128 billion memory parameters during pretraining. Zero-gradient writes are Larimar's contribution, IBM and Princeton, ICML 2024. Reading a frozen datastore at inference time traces back to kNN-LM, Khandelwal et al. INLAY sits in the same family as SERAC, GRACE, and WISE, memory based editors that leave the base model frozen, and the honest claim is at the mechanism level, not the paradigm level.

What differs from its nearest neighbors: SERAC routes to a separate generator model, GRACE replaces a hidden activation directly, WISE merges a copied FFN subspace. INLAY instead adds the stored answer's unembedding directions straight into the output logits, no auxiliary model, no activation surgery, no weight change. And the addressing path has zero trained parameters anywhere in it, where GRACE keys on raw activations that this project measured to be subject and topic entangled, and SERAC and WISE both train their routing.

The engineering reality, the part that doesn't show up in a results table

Getting trustworthy numbers out of a method like this took real debugging, not just running scripts, and it is worth being honest about what actually went wrong along the way rather than presenting a clean story that never happened.

  • A disk filling up mid-download silently truncated a cached model to a third of its real size, which surfaced later as a completely unrelated-looking crash in a different method entirely, until the actual cause, three missing weight shards, was traced back to the original disk-full event.
  • A stale cached projection matrix, sized for one model, got silently reused when a different model's run started, because the cache path didn't include the model name. The symptom was a matrix-shape mismatch several layers deep in someone else's editing code, not an obviously wrong input.
  • Restarting a stopped cloud instance wipes its ephemeral local disk but not its home directory, so a symlink that used to point at a real model snapshot kept existing and kept looking valid, while the thing it pointed to was simply gone.
  • A tokenizer difference between model families, one architecture silently prepending a beginning of sequence token where another didn't, corrupted every stored answer's semantic key without ever raising an error. The visible symptom was flat, suspiciously low accuracy across every alpha value tried, which looked like a calibration problem for a while before it was recognized as a tokenization bug. Fixing one line took the score from 0.15 to 0.90 on the spot.
  • A process wait condition written with a regex alternation that the shell's pattern matcher didn't actually support let two GPU jobs launch at once and run out of memory fighting over the same card, instead of running one after the other as intended.

None of these were subtle research questions. They were the ordinary friction of running real experiments on rented infrastructure, and the reason they're listed here rather than smoothed over is that every one of them could plausibly have produced a wrong number that looked fine if it hadn't been caught.

How the numbers were kept honest

Every headline score comes from a held out gate selection protocol: a tune split picks the operating threshold, and the test split, which the threshold was never fit to, is what gets reported. RippleEdits results use a matched manifest, the identical set of wikidata verified subjects run through every method being compared, specifically so no method gets an easier or harder sample than another. Baselines are scored through the same EasyEdit harness INLAY is compared against, not a custom scorer that might quietly favor one side.

The code itself was also audited directly rather than trusted on the strength of its comments. Two real defects turned up: the read path has two functions that apply different gating logic to the same decision, one honors the margin and relation gates and one doesn't, and the product key allocator only ever fills the diagonal of its table, giving it a real capacity of a few thousand slots rather than the millions its own documentation claims. Tracing through every benchmark script confirmed neither defect has actually touched a published number, every current benchmark writes at most one fact per memory table before scoring it, which makes the margin gate structurally inert regardless of which function is called, and no run has ever come close to the real diagonal capacity limit. Both are real bugs worth fixing before any capacity claim goes in front of a reviewer, and neither is quietly sitting inside the numbers in this report.

What's still genuinely unresolved

Three things, stated plainly rather than buried in a footnote. The product key allocator needs a real fix, either a proper two dimensional slot assignment or, more honestly given the scale actually used so far, dropping the product key framing for exact dense retrieval until profiling shows it's actually a bottleneck. The two gating code paths need to be unified into one shared decision function before any experiment writes more than one fact into the same table, which is exactly the regime where they'd start to disagree. And RippleEdits remains the one benchmark where INLAY honestly loses to plain in-context retrieval, because playing back a stored answer is not the same operation as deriving what follows from it, and no amount of better addressing changes that basic fact about what the method is doing.
